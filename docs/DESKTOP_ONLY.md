# 桌面原生连接与自动更新

0.5.4 默认且仅使用正式安装的 ZCode Desktop 宿主创建会话，`default_transport` 固定为 `desktop_native`，`desktop_native_enabled` 默认启用。公共工具参数只接受 `desktop_native`；显式 `engine`、旧独立 SID 恢复及底层独立 Client 启动均被拒绝。

## 使用哪个 ZCode

- 正式安装的唯一主进程已运行：直接复用，不再启动另一个进程来转发打开项目的请求。
- 主程序未运行：在允许自动启动时，只启动本机配置的已安装可执行文件；不会复制应用，也不会运行后台 `app-server --stdio` 任务引擎。
- 多个主实例、可执行文件不符或进程身份无法读取：明确报错，不猜测或另开。
- 状态查询与后台观察不启动应用。新会话和模型查询在需要时可按自动启动设置启动正式主程序。

Windows 下使用系统命名锁协调并发启动请求。GPU、渲染进程和属于 Desktop 的内部脚本工作进程不算额外主实例；它们由应用自己管理。桥接还核对私有宿主报告的可执行文件，避免连接到另一个安装。

当前唯一主进程识别和正式安装接入的验证平台是 Windows，接入门禁针对 Desktop 3.18.2。缺少接入、版本不兼容或平台不支持时停止并给出诊断。

## 会话为什么能自动更新

原生会话通过 Desktop 自己的会话服务创建，归属其运行时；后续消息和任务状态走桌面正常的事件链路。匹配到唯一已有项目时归入该项目，无匹配时位于未归属“任务”分组；分组可能折叠或在滚动区域外。会话持久化、项目归属和实际 GUI 可见仍分别判断，不用创建成功冒充肉眼验收。

旧设置里的“Desktop 同步（可选）”用于独立引擎会话的补同步，它不控制原生会话更新。0.5.4 已从原生设置页和内嵌面板移除该组配置，并拒绝重新启用旧补同步。

## 升级

1. 更新插件以及正式安装的兼容 Desktop 接入，保留本机 control、认证和 ownership。
2. 加载新版 Desktop 宿主；已经加载旧 JS 的进程需要重启 ZCode，插件不会擅自重启用户应用。
3. 重载桥接服务。`zcode_status` 返回实际版本、`transport=desktop_native`、`independent_engine_enabled=false`，不会为检查状态启动独立引擎。

只更新 GitHub 源码或安装包不会替换已运行进程中的代码。Codex 的设置页若仍缓存旧插件界面，需要重新载入插件；必要时重启 Codex 刷新。桥接后台可单独重载，原生任务由 Desktop 管理。

旧 engine 会话记录保留，不能通过新版本恢复或跨引擎接管。新任务的旧后端偏好迁移为原生；模型和思考强度仍使用真实配置，不替换模型。

工作区黑名单仍默认只禁用 C 盘及其子路径，详见 [工作区规则](WORKSPACE_POLICY.md)。它限制工作区选择，不构成模型文件访问隔离。
